# 0.3 — venv and uv

> **One-line summary:** Virtual environments isolate a project's dependencies from the rest of the system. `uv` manages them in milliseconds and replaces `pip`, `venv`, `pip-tools`, and `pyenv` with a single fast tool.

## 🎯 Learning Goals

By the end of this lesson you will be able to:

- [ ] Explain **why** virtual environments exist (the dependency hell problem)
- [ ] Create, activate, and deactivate a **`venv`** manually
- [ ] Create a project with **`uv init`** and manage dependencies with **`uv add`**
- [ ] Understand **`pyproject.toml`** vs **`uv.lock`** vs **`.venv/`**
- [ ] Know what **`uv sync`**, **`uv run`**, and **`uv pip`** do
- [ ] Explain the difference between **`venv`** (built-in) and **`uv venv`**
- [ ] Avoid the top 10 dependency management mistakes
- [ ] Know how to make your project **reproducible** for someone else

## 📖 The Full Explanation

### 1. The problem: dependency hell

Imagine you're building two Python projects:

- **Project A** needs `requests==2.28.0` (an old version, because it uses a deprecated API)
- **Project B** needs `requests==2.32.0` (the latest, with a security fix)

If both projects share the **same** Python installation, `pip install requests==2.28.0` overwrites whatever was there. Now Project B is broken. You install `2.32.0` to fix B, and A breaks. **This is dependency hell.**

The problem gets worse:
- Different projects need different **Python versions** (some old ML code needs 3.8, new code needs 3.12)
- Transitive dependencies (your library depends on another library depends on another) can conflict in subtle ways
- Upgrading one package silently breaks three others

**The industry answer:** *isolate every project*. Each project gets its own **virtual environment** — a directory containing:
- Its own Python interpreter (or a symlink to one)
- Its own `site-packages/` with its own installed libraries
- Its own `pyvenv.cfg` marker file

When you "activate" a virtual environment, your shell's `python` and `pip` point to *that* environment's copy. When you "deactivate", they go back to the system. Every project is an island. No conflicts. Ever.

**The historical stack:** Python ships with `venv` (built-in). Before `venv`, there was `virtualenv` (still exists, faster historically). Before `uv`, the standard workflow was:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install requests
pip freeze > requirements.txt
```

That's 4 commands, ~10–30 seconds, plus the pip cache warming up. For a big project, `pip install` can take **minutes**.

**The modern stack:** `uv` collapses all of that to *milliseconds*.

### 2. The built-in `venv` — how it actually works

The **`venv`** module is included in Python's standard library. It creates virtual environments.

**Create one:**

```powershell
python -m venv .venv
```

This creates a `.venv/` folder in the current directory containing:
```
.venv/
├── Scripts/              ← Windows executables (Linux/macOS: bin/)
│   ├── python.exe        ← the interpreter for this env
│   ├── pip.exe
│   ├── activate.bat
│   ├── Activate.ps1      ← PowerShell activation script
│   └── ...
├── Lib/
│   └── site-packages/    ← installed libraries go here
└── pyvenv.cfg            ← marker file
```

**Activate it (PowerShell):**

```powershell
.\.venv\Scripts\Activate.ps1
```

Your prompt changes to:

```
(.venv) PS C:\Users\you\python-playground>
```

The `(.venv)` prefix means you're inside the environment. Now:

```powershell
python --version        # uses .venv/Scripts/python.exe
pip install requests    # installs into .venv/Lib/site-packages
where python            # confirms path points into .venv
```

**Deactivate:**

```powershell
deactivate
```

The `(.venv)` prefix disappears, and `python` points back to the system installation.

**Why bother, if `uv` exists?**  
Because you'll encounter `venv` **everywhere** — in CI scripts, in legacy repos, in job interviews. Understanding the mechanics means you'll never be lost when a tool acts up.

**Gotcha:** `.venv/` should **never** be committed to git. It's machine-specific and can be hundreds of MB. Add it to `.gitignore`. What *is* committed is the *recipe* (`pyproject.toml` + `uv.lock` or `requirements.txt`) that rebuilds `.venv/` on any machine.

### 3. Enter `uv` — the modern Python toolchain

We installed `uv` in Lesson 0.2. Now let's actually use it. `uv` has **three modes** of operation:

1. **`uv pip`** — drop-in pip replacement for existing workflows
2. **`uv init` + `uv add` + `uv sync`** — full project management (recommended for new projects)
3. **`uv tool`** — global CLI tool installation (replaces `pipx`)

We'll cover mode 1 briefly (for compatibility), then focus on mode 2 (which is what modern Python projects use).

#### Mode 1 — `uv pip` (compatibility mode)

If you have a `.venv` activated, `uv pip` behaves exactly like `pip`, but faster:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
uv pip install requests
```

**Speed:** `uv pip install requests` typically completes in **under 100ms** (warm cache) vs **~1–3s** for `pip`. For large requirements files, `uv` is often **10–100x faster**.

**When to use mode 1:** legacy projects with `requirements.txt`, quick scripts, one-off installs. If you see `pip install X` in a tutorial, you can often replace it with `uv pip install X` and get the same result — faster.

#### Mode 2 — project mode (recommended)

This is the modern way. Instead of `pip install`, you **declare dependencies** in `pyproject.toml`, and `uv` figures out the rest.

**Step 1 — Create a project:**

```powershell
uv init my-first-project
cd my-first-project
```

This creates:

```
my-first-project/
├── .python-version        ← which Python version this project needs
├── pyproject.toml         ← project metadata + dependencies
├── README.md
└── src/
    └── my_first_project/
        └── __init__.py
```

**Notice:** no `.venv/` yet! `uv` creates it lazily on first use.

**Step 2 — What's inside `pyproject.toml`?**

```toml
[project]
name = "my-first-project"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = []
```

This file is the **single source of truth** for the project. The `dependencies = []` list will grow as you add packages.

**Step 3 — Add a dependency:**

```powershell
uv add requests
```

What just happened (all in ~200ms):
1. `uv` created `.venv/` (if not existing)
2. Resolved the full dependency tree (requests + its transitive deps)
3. Downloaded and installed everything into `.venv/`
4. Updated `pyproject.toml` with `dependencies = ["requests>=2.32.0"]`
5. Created `uv.lock` — the **lock file** with exact versions of everything

Now `pyproject.toml` looks like:

```toml
[project]
name = "my-first-project"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["requests>=2.32.0"]
```

**Step 4 — Use the environment:**

```powershell
uv run python -c "import requests; print(requests.__version__)"
```

`uv run` is **magic**: it activates the virtual environment *just for this command*, runs the command, then the environment goes away. You don't need to `activate` first. This is *the* recommended workflow — **avoid manual `activate` / `deactivate`** entirely.

Or run a script:

```powershell
uv run python src/my_first_project/main.py
```

**Step 5 — Reproduce on another machine:**

Someone clones your repo. They run:

```powershell
uv sync
```

`uv` reads `uv.lock`, installs the **exact versions** locked in, and creates `.venv/`. **Bit-for-bit identical environment.** This is what "reproducible" means in practice.

### 4. The three files you must understand

Every `uv` project has these three pillars:

| File | Purpose | Commit to git? |
|---|---|---|
| **`pyproject.toml`** | Human-written spec: project name, Python version constraint, direct dependencies | ✅ **Yes** |
| **`uv.lock`** | Machine-written lock: exact versions + hashes of every transitive dep | ✅ **Yes** |
| **`.venv/`** | The actual installed environment (can be 100MB+) | ❌ **No** (gitignore) |

**Why commit `uv.lock`?**  
Because `pyproject.toml` says `requests>=2.32.0` — *which* 2.32.x? Which transitive dependencies? The lock file records the *exact* resolution so every developer and every CI run uses the **same versions**. Without it, `pip install` (or `uv sync` in non-locked mode) could resolve slightly differently on different days, leading to "works on my machine" bugs.

**Why not commit `.venv/`?**  
Because it contains OS-specific binaries, absolute paths, and machine-specific state. It's regenerated by `uv sync` in seconds.

**Why commit `.python-version`?**  
It's a single-line file like `3.12` or `3.12.7`. It tells `uv` which Python version to use for this project. `uv` will download and install that version automatically if you don't have it. **Yes, `uv` manages Python versions themselves.** No more `pyenv` on Windows.

### 5. `uv` commands you'll use daily

Here's the table I keep on my second monitor:

| Command | What it does |
|---|---|
| `uv init <name>` | Create a new project |
| `uv add <pkg>` | Add a dependency (updates `pyproject.toml` + `uv.lock` + `.venv`) |
| `uv add --dev <pkg>` | Add a **dev dependency** (pytest, ruff, mypy — not shipped to prod) |
| `uv remove <pkg>` | Remove a dependency |
| `uv sync` | Install exactly what's in `uv.lock` (or resolve fresh if missing) |
| `uv lock` | Update `uv.lock` without installing |
| `uv run <cmd>` | Run a command inside the project's venv |
| `uv run python script.py` | Run a Python script in the project's venv |
| `uv python install 3.12` | Download + install Python 3.12 (managed by `uv`) |
| `uv python list` | List installed Python versions |
| `uv python pin 3.12` | Set the project's Python version (writes `.python-version`) |
| `uv tool install <pkg>` | Install a CLI tool globally (e.g., `ruff`, `httpie`) |
| `uv tree` | Show the dependency tree |
| `uv pip list` | Like `pip list`, but faster |

**`uv run`** is the workhorse. Every command you run *inside* a project should go through `uv run`. Example:

```powershell
uv run pytest                          # run tests
uv run python -m my_first_project      # run module
uv run ruff check .                    # run linter
uv run python -c "print('hi')"         # one-liner
```

You never need to `activate` a `.venv` again. `uv run` handles it per-command. Your shell prompt stays clean, your environment stays isolated.

### 6. The `pyproject.toml` — a real example

Here's what a mature project's `pyproject.toml` looks like:

```toml
[project]
name = "my-first-project"
version = "0.1.0"
description = "Learning Python the right way"
readme = "README.md"
requires-python = ">=3.12"
authors = [{ name = "Your Name", email = "you@example.com" }]
license = { text = "MIT" }

dependencies = [
    "requests>=2.32.0",
    "httpx>=0.27.0",
]

[dependency-groups]
dev = [
    "pytest>=8.0.0",
    "ruff>=0.8.0",
    "mypy>=1.13.0",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 88
target-version = "py312"

[tool.pytest.ini_options]
testpaths = ["tests"]
```

**Sections explained:**

- **`[project]`** — metadata + runtime dependencies (`dependencies = [...]`)
- **`[dependency-groups] dev = [...]`** — dev-only dependencies (installed with `uv sync --dev`, not shipped to users)
- **`[build-system]`** — how to *build* the package (hatchling, setuptools, poetry-core, uv-build)
- **`[tool.ruff]`**, **`[tool.pytest.ini_options]`**, etc. — tool-specific config, all in one file

**Why `pyproject.toml` matters:** it's the **PEP 621** standard. Every modern tool (`pip`, `uv`, `poetry`, `hatch`, `ruff`, `mypy`, `pytest`, `pylint`) reads it. One file to rule them all.

**Historical note:** Before `pyproject.toml`, we had `setup.py`, `setup.cfg`, `requirements.txt`, `tox.ini`, `pytest.ini`, `.flake8`, `mypy.ini`, and more — each tool with its own config file. `pyproject.toml` unified them. That's why you'll see it in every serious project.

### 7. `uv sync` vs `uv run` vs activation — when to use which

This trips up everyone at first. Here's the decision tree:

```
Do you want to run ONE command inside the project?
  → uv run <command>

Do you want a NEW Python environment matching uv.lock?
  → uv sync

Do you want an interactive shell inside the venv (for many commands)?
  → uv run python
  (or, rarely: .venv\Scripts\Activate.ps1)
```

**My recommendation:** use **`uv run`** for everything. Never manually activate.

**Why?**
- No accidental "I'm in the wrong venv" bugs
- Shell history stays clean
- CI scripts work identically to local shells
- REPL access is one command away: `uv run python`

**Exception:** when you're doing heavy exploration with many commands in a row, activation can be faster because `uv run` has ~30ms overhead per call. But that's a micro-optimization; correctness > 30ms.

### 8. The `.gitignore` for a `uv` project

Your `.gitignore` for a `uv` project looks like this:

```gitignore
# Python
__pycache__/
*.py[cod]
*$py.class

# venv — NEVER commit
.venv/
venv/
ENV/
env/

# uv
# (uv.lock SHOULD be committed — see gotchas)
# (.python-version SHOULD be committed — see gotchas)

# Testing
.pytest_cache/
.coverage
htmlcov/

# Type checking
.mypy_cache/
.pyright/

# Linting
.ruff_cache/

# Jupyter
.ipynb_checkpoints/

# IDE
.vscode/
.idea/

# OS
.DS_Store
Thumbs.db

# Build artifacts
dist/
build/
*.egg-info/

# Environment variables
.env
.env.local
```

**Critical:** `.venv/` is ignored. `uv.lock`, `pyproject.toml`, and `.python-version` are **committed**.

**Exercise 1 — Create your first `uv` project.**  
In PowerShell:

```powershell
cd $HOME
uv init hello-uv
cd hello-uv
```

You should see:

```
Initialized project `hello-uv` at `C:\Users\you\hello-uv`
```

Open `pyproject.toml` in VS Code and confirm it looks like the example above.

**Exercise 2 — Add a dependency and use it.**

```powershell
uv add requests
uv run python -c "import requests; r = requests.get('https://httpbin.org/get'); print(r.status_code)"
```

Expected output:

```
200
```

This proves the environment works, the dependency is installed, and `uv run` activated everything correctly.

**Exercise 3 — Add a script and run it.**  
Create `src/hello_uv/main.py`:

```python
# src/hello_uv/main.py
"""First real uv project script."""
import sys
import platform


def main() -> None:
    print("=" * 50)
    print("Hello from uv!")
    print("=" * 50)
    print(f"Python:  {platform.python_implementation()} {sys.version.split()[0]}")
    print(f"Exe:     {sys.executable}")
    print(f"Project: hello-uv")
    print("=" * 50)


if __name__ == "__main__":
    main()
```

Run it:

```powershell
uv run python src/hello_uv/main.py
```

**Exercise 4 — Reproduce the environment.**  
Simulate a teammate cloning your project:

```powershell
# Save the current state
Get-Content uv.lock | Select-Object -First 5

# Delete the environment
Remove-Item -Recurse -Force .venv

# Rebuild from lock
uv sync

# Confirm it works
uv run python -c "import requests; print(requests.__version__)"
```

**Exercise 5 — Add a dev dependency.**

```powershell
uv add --dev pytest
uv run pytest --version
```

Notice: `pytest` is not in `dependencies` in `pyproject.toml` — it's in `[dependency-groups] dev`. That means it won't ship to users of your library, but it's available during development.

**Exercise 6 — Manual `venv` comparison.**  
For comparison, create a manual `venv` project:

```powershell
mkdir manual-venv-demo
cd manual-venv-demo
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install requests
python -c "import requests; print(requests.__version__)"
deactivate
cd ..
```

Compare the speed and number of commands to `uv add requests`. Note the differences in your learning notes.

## ⚠️ Gotchas & Traps

1. **Committing `.venv/` to git.**  
   → It contains OS-specific binaries and absolute paths. Commits are huge and useless. Add to `.gitignore`.

2. **Committing `uv.lock` to git? — YES, DO IT.**  
   → The lock file is the **point** of reproducible builds. Commit it. It's a feature, not a bug. Many beginners see the giant file and think it's generated; it **is** generated but you must commit it. This is exactly like `package-lock.json` in Node.js or `poetry.lock` in Poetry.

3. **Committing `.python-version` to git.**  
   → Yes, commit this. It's the recipe for which Python version to use. `uv` will install that version automatically if missing.

4. **Confusing `pip install` with `uv add`.**  
   → `pip install` installs into the current environment but does *not* update `pyproject.toml`. `uv add` installs **and** updates the manifest **and** the lock file. If you use `pip install`, your teammate running `uv sync` will not get the package.

5. **Using `uv pip install` inside a `uv` project.**  
   → It works, but it bypasses the lock file. In a project, prefer `uv add`. `uv pip` is for legacy scripts and `requirements.txt` workflows.

6. **Forgetting `uv run` and typing `python` instead.**  
   → In a `uv` project, `python` without activation uses the **system Python**, not the project's `.venv`. Always use `uv run python`. This catches everyone at least once.

7. **Manually activating `.venv` and then running `uv add`.**  
   → It works, but `uv` *already* manages activation via `uv run`. Manual activation plus `uv` commands creates occasional confusion. Simplest rule: **never manually activate; always `uv run`.**

8. **Multiple Python versions conflicting via `.python-version`.**  
   → If your `.python-version` says `3.12` but you have `3.12.1` and `3.12.7` installed, `uv` picks the closest. If it says `3.13` and you don't have 3.13, `uv` downloads it automatically. This is what `pyenv` used to do — now built into `uv`.

9. **Editing `uv.lock` by hand.**  
   → Never. It's generated and `uv` will overwrite it. If you need to change a version, use `uv add pkg@version` or `uv lock --upgrade-package pkg`.

10. **Thinking `requirements.txt` is dead.**  
    → It's still used in many legacy projects and simple deployments. But **for new projects**, `pyproject.toml` + `uv.lock` is the modern standard. We'll cover `requirements.txt` when relevant (Module 7.4).

11. **The `uv` cache location.**  
    → `uv` caches downloaded packages in `%LOCALAPPDATA%\uv\cache\`. It can grow to several GB. `uv cache clean` clears it. It's safe to delete at any time — it just redownloads. Do **not** delete the `.venv/` thinking it's "part of the cache" — that's the project's environment.

12. **Using `uv tool install` for project dependencies.**  
    → `uv tool install` installs a CLI tool **globally**, outside any project. Use it for tools like `ruff`, `httpie`, `black` — not for project libraries. Project dependencies go through `uv add`.

## 🧪 Practice

**1. The "fresh clone" test.**  
Create a project, then delete `.venv/` and pretend you just cloned it. Run `uv sync` and verify it works. **This is exactly what your teammate will do.**

**2. Dependency inspection.**  
In `hello-uv`, run:

```powershell
uv tree
```

Answer: which direct dependencies does `requests` bring in transitively? How many packages total?

**3. Speed comparison.**  
Time `pip install requests` (in a manual venv) vs `uv add requests` (in a fresh `uv` project). Write down the numbers. The difference is usually **5–20x** on a warm cache, more on a cold one.

**4. Delete the venv test.**  
Run `Remove-Item -Recurse -Force .venv`, then `uv run python -c "import requests; print('ok')"`. Answer: what did `uv` do automatically?

**5. Reproducibility test.**
- `uv add requests`
- Save `uv.lock`
- `uv remove requests`
- `uv sync` (note: requests is gone, environment is clean)
- Restore `uv.lock` from git / backup
- `uv sync` — verify `requests` is back at the exact same version

**6. Reflection (in notes):**
- What's the difference between `pip install` and `uv add`?
- Why commit `uv.lock` but not `.venv/`?
- Why use `uv run` instead of activating the venv?
- What would happen if you didn't commit `uv.lock`? (Hint: "works on my machine")

**7. Exploit the `uv` mode 1.**
For any existing `requirements.txt` file you have lying around, try:

```powershell
python -m venv .venv
uv pip install -r requirements.txt
```

Note how much faster it is than `pip install -r`. This is useful even in legacy projects.
