# 0.1 — What is Python?

> **One-line summary:** Python is a high-level, dynamically-typed, general-purpose programming language whose design philosophy prioritizes readability — and whose ecosystem made it the default language of AI and data.

## 📖 The Full Explanation

### 1. What is Python, really?

Python is a **programming language specification**. That's the key idea most beginners miss.

A **specification** is a document that says: *"if you write code that looks like this, it should behave like that."* It doesn't say *how* the computer executes it. That's the job of an **implementation**.

Think of it like HTML:
- **HTML** is a specification — it says what `<h1>` means
- **Chrome, Firefox, Safari** are implementations — they each *build* a browser that follows the spec

Python is the same:
- **Python** (the language) = the spec (defined in the [Python Language Reference](https://docs.python.org/3/reference/))
- **CPython, PyPy, Jython, MicroPython, IronPython** = implementations

So when someone says *"Python is slow"*, they usually mean *"**CPython** is slow"* — because CPython is the default implementation everyone uses, but PyPy (another implementation) can be **4–10x faster** in some workloads.

Its last release was January 1, 2020. Don't learn it, don't use it, don't read old StackOverflow answers that use it.

### 3. The Zen of Python (PEP 20)

Open a Python REPL (we'll set that up properly in Lesson 0.2) and type:

```python
import this
```

You'll get 19 aphorisms that define the language's soul. The most important ones:

```
Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
Complex is better than complicated.
Readability counts.
There should be one-- and preferably only one --obvious way to do it.
If the implementation is hard to explain, it's a bad idea.
```

Why care? Because these principles are why Python code looks the way it does. When you see Python code that's ugly or clever-but-unreadable, it's un-Pythonic. The community actively pushes back against cleverness. This is a core cultural difference from languages like Perl or C++.

Trick: import this prints the Zen. import antigravity opens a webcomic in your browser. Both are Easter eggs baked into Python itself — a hint that the language is meant to be fun.

4. What actually happens when you run python script.py?

This is the most important mental model to build before writing any code. Here's the real pipeline:

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌─────────────┐
│  source.py   │───▶│   Compiler   │───▶│  bytecode    │───▶│     PVM     │
│  (your code) │    │  (frontend)  │    │  (.pyc file) │    │  executes   │
└──────────────┘    └──────────────┘    └──────────────┘    └─────────────┘
```

Step by step:

1. You write hello.py — plain text, your source code
2. CPython compiles it to bytecode — an intermediate representation (not machine code!)
3. Bytecode is cached in a __pycache__/ folder as .pyc files
4. The Python Virtual Machine (PVM) reads bytecode and executes it instruction by instruction

Consequences you should know:

· ✅ Python is compiled (to bytecode) — the "interpreted" label is a simplification
· ✅ Python is interpreted (bytecode → execution by the PVM, not native CPU instructions)
· ⚠️ CPython is not fully interpreted and not fully compiled — it sits in the middle
· ⚠️ The .pyc files are why your second run of a script can be faster than the first
· ⚠️ __pycache__/ is not something you commit to git — it's ignored in our .gitignore

Why this matters for performance: Bytecode is slower than native machine code because the PVM has to interpret each bytecode instruction. This is a big part of why CPython is slower than C, Rust, or Go. PyPy fixes this with a JIT (Just-In-Time) compiler that compiles hot loops to native code on the fly.

---

5. Python "interpreted" vs "compiled" — the honest answer

Most tutorials say: "Python is an interpreted language, C is a compiled language." That's half-true. Here's the accurate picture:

Language Typical pipeline
C source → machine code → CPU directly
Java source → bytecode → JVM (JIT)
Python source → bytecode → PVM (no JIT in CPython by default)
PyPy (Python impl) source → bytecode → JIT → machine code

Java and Python are structurally similar (both compile to bytecode). The difference is that Java's JVM has a JIT compiler while CPython's PVM does not. That's the real reason for the perf gap.

Gotcha: People say "Python is interpreted" meaning "there's no separate compile step you run manually" — which is true from the user's perspective. But technically, CPython compiles to bytecode every time you run a script (and caches the result). So "interpreted" is a usage label, not an architecture label.

6. The GIL — a first mention

GIL = Global Interpreter Lock. In CPython, only one thread can execute Python bytecode at a time. Even on an 8-core machine, a pure-Python CPU-bound program using threading uses one core.

This is the single biggest architectural quirk of CPython. It exists to make memory management (reference counting) safe without per-object locks.

We will cover the GIL in depth in [[9.1 GIL]] — for now, just know:

· The GIL is a CPython thing (PyPy, Jython have different behavior)
· It does not prevent parallelism if you use multiprocessing or asyncio properly
· Python 3.13 (2024) ships an experimental free-threaded build (PEP 703) that removes the GIL — but it's not production-ready yet

7. Why Python dominates AI and Data

This is a fair question: "Why Python and not C++, which is way faster?"

The answer isn't the language — it's the ecosystem:

Reason Explanation
NumPy/Pandas Vectorized C code under a friendly Python API — you write Python, it runs at C speed
PyTorch/TensorFlow The AI frameworks are written in C++/CUDA underneath, exposed via Python
Readability Researchers can iterate fast; Python code reads almost like pseudocode
glue language Python connects to C/C++/Fortran libraries — it's the "duct tape of computing"
Community Every AI paper ships with Python code. Every tutorial is in Python
Notebooks Jupyter = interactive Python, perfect for data exploration

Key insight: Python's slowness doesn't matter in AI because the heavy lifting is done by C/CUDA libraries. Python is just the orchestration layer. Your model.fit(X, y) line calls into optimized C++ that was written by experts.

8. The four implementations you should know

Implementation What it is When you'd care
CPython The reference implementation, written in C. You're almost certainly using this. Default for 99% of Python work
PyPy Written in RPython, has a JIT compiler. Often 4–10x faster for pure-Python CPU-bound code. When CPython is too slow and you can't use C extensions
Jython Runs on the JVM, integrates with Java Rare — mostly legacy enterprise
MicroPython Tiny Python for microcontrollers (ESP32, Raspberry Pi Pico) Embedded/IoT work
IronPython Runs on .NET CLR Rare — mostly legacy .NET integration

For 99.9% of learners: use CPython, ignore the rest for now. Just know they exist so you don't get confused when you see the names.

⚠️ Gotchas & Traps

These are the mistakes beginners (and even intermediate devs) make:

1. "Python is interpreted, so there's no compilation step."
      → False. CPython compiles to bytecode on every run. It just doesn't produce a standalone .exe. The .pyc files in __pycache__/ are compiled artifacts.
2. "Python is slow."
      → CPython is slow for pure-Python CPU-bound code. But 90% of real Python code calls C libraries (NumPy, PyTorch, requests) — so Python's orchestration overhead is negligible. Also: PyPy exists.
3. "Python 2 and Python 3 are compatible."
      → They are not. print is a function in Python 3 (print("x")), a statement in Python 2 (print "x"). String handling is completely different (Unicode vs bytes). If a tutorial uses Python 2 syntax — close the tab.
4. "I should learn Python 2 first, then 3."
      → Never. Python 2 has been dead since January 1, 2020. No security patches, no new features, no community support. Learn Python 3 exclusively.
5. "The GIL means Python can't do multithreading."
      → The GIL means CPython bytecode can't run in parallel across threads. But threading still works for I/O-bound tasks (network, disk). And multiprocessing bypasses the GIL entirely. And asyncio exists. We'll cover all this in Module 9.
6. "PyPy is a Python version."
      → No. PyPy is an implementation of Python. It runs the same Python language, but with a JIT compiler. You don't write different code — you just use a different interpreter.
7. Committing __pycache__/ to git.
      → Don't. It's regenerated on every run and pollutes your repo. Our .gitignore already handles this.
