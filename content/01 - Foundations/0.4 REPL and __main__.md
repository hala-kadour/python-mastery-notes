# 0.4 — REPL and `__main__`

> **One-line summary:** The REPL is a live Python shell. `if __name__ == "__main__":` is the idiom that lets a file behave *differently* when run directly vs when imported — and it's the first time you see Python's module system at work.

## 🎯 Learning Goals

By the end of this lesson you will be able to:

- [ ] Use the REPL effectively: history, autocomplete, `_`, `dir()`, `help()`, `exit()`
- [ ] Explain the difference between **REPL mode** and **script mode**
- [ ] Understand `__name__` — what it is and what it holds in each context
- [ ] Write and explain `if __name__ == "__main__":` from first principles
- [ ] Know *why* the idiom exists (the import side-effect problem)
- [ ] Recognize the pattern in real code (Flask, pytest, scripts, packages)
- [ ] Avoid the top traps (missing guard, `from script import *`, circular imports)

## 📖 The Full Explanation

### 1. What is a REPL, really?

**REPL** stands for **R**ead–**E**val–**P**rint **L**oop. It's an interactive interpreter:

1. **Reads** a line of code you type
2. **Evaluates** it (runs it)
3. **Prints** the result (unless it's `None`)
4. **Loops** back for the next input

You open it with:

```powershell
uv run python
```

You'll see:

```
Python 3.12.x (main, ...) [MSC v.1938 64 bit (AMD64)] on win32
Type "help", "copyright", "credits" or "license" for more information.
>>>
```

The `>>>` is the **primary prompt**. A `...` is the **continuation prompt** — Python is waiting for you to finish a multi-line block (an `if`, a function, a loop).

```python
>>> if True:
...     print("hi")
...
hi
>>>
```

**Exit:** `exit()` or `quit()` or `Ctrl+Z` then Enter (Windows) / `Ctrl+D` (Linux/macOS).

---

### 2. REPL power features (most people never learn these)

The REPL is **vastly** more powerful than "type a line, get a result." Here's the full arsenal:

#### `_` — the last result

```python
>>> 10 + 5
15
>>> _ * 2
30
>>> _ + 1
31
```

`_` holds the **last printed value**. Useful for chained math without reassigning.

#### `dir()` — what can this object do?

```python
>>> dir("hello")
['__add__', '__class__', '__contains__', ..., 'capitalize', 'casefold', 'center', ...]
>>> dir([])
['__add__', '__class__', ..., 'append', 'clear', 'copy', 'count', 'extend', ...]
```

Every method of an object. **This is how you discover the API of any object** without googling.

#### `help()` — the built-in documentation

```python
>>> help(str.split)
Help on method_descriptor:

split(self, /, sep=None, maxsplit=-1)
    Return a list of the words in the string, using sep as the delimiter string.
    ...
```

`help(obj)` shows docstrings. `help()` with no argument enters an interactive help browser (`quit` to exit). **This is offline documentation, always available.**

#### Tab autocomplete

```python
>>> import json
>>> json.<TAB>
```

Pressing **Tab** after a `.` lists all attributes. In PowerShell (without readline), this may not work; use `py -m readline` or install `pyreadline3`. In VS Code's integrated terminal, it usually does.

#### `?` — IPython/Jupyter only

In **IPython** (and Jupyter notebooks), you get **even more**:

```python
In [1]: str.split?
# shows signature + docstring

In [2]: str.split??
# shows source code

In [3]: %timeit sum(range(1000))
# benchmarks the expression

In [4]: %history
# shows all past commands

In [5]: !ls
# runs a shell command
```

**When to use IPython/Jupyter:** data exploration, ML, anything interactive. We'll come back to this in Module 11.

#### `repr()` vs `print()` in the REPL

```python
>>> "hello"
'hello'       ← REPL prints repr(), so quotes appear
>>> print("hello")
hello         ← print() prints str(), no quotes
```

**Why this matters:** In the REPL, `>>> obj` shows `repr(obj)`, which is the *developer-facing* representation (usually with type hints and quotes). `print(obj)` shows `str(obj)`, the *human-facing* representation. This is a **fundamental distinction** we'll revisit in Module 4 (OOP) when we define `__repr__` and `__str__`.

#### History — `↑` / `↓`

Press the **up arrow** to recall previous commands. Down to go forward. This works in PowerShell if `pyreadline3` is installed; always works in VS Code's terminal.

#### `Ctrl+L` — clear the screen

Keeps your history, clears the display.

#### `Ctrl+C` — interrupt

Kills the currently running command without exiting the REPL.

**Try this exercise right now:**

```python
>>> import time
>>> time.sleep(10)   ← now press Ctrl+C
KeyboardInterrupt
>>>
```

You get back to the prompt immediately.

### 3. REPL vs script mode — a real difference

| Aspect | REPL | Script |
|--------|------|--------|
| **Input** | line by line, interactive | file on disk, run top-to-bottom |
| **Output** | prints every expression's value | only what you explicitly `print()` |
| **`__name__`** | `"__main__"` | `"__main__"` if run directly, `"<module-name>"` if imported |
| **Persistence** | variables live until exit | nothing after the script exits |
| **Multi-line blocks** | use `...` continuation | just write them on multiple lines |
| **Debugging** | ideal | harder |
| **Save/reuse** | ❌ no | ✅ yes |

**The most important difference to internalize:**

In the **REPL**:

```python
>>> 2 + 2
4
```

The `4` is printed automatically because the REPL **echoes every expression's value**.

In a **script**:

```python
# script.py
2 + 2
```

Run it — **nothing prints**. The expression is evaluated but the result is discarded. To see it, use `print()`:

```python
# script.py
print(2 + 2)
```

**Why?** Because a script is just a sequence of statements — the interpreter has no idea which results you care about. `print()` is explicit. This is the difference between *interactive* and *batch* execution.

**REPL is for thinking; scripts are for doing.**

### 4. The `__name__` variable — the heart of this lesson

Every Python module has a **global variable** named `__name__`. It holds a string. What string? It depends on **how the module was executed**.

Let's experiment. Create two files in your `python-playground/`:

**File 1 — `who_am_i.py`:**

```python
# who_am_i.py
print(f"The __name__ is: {__name__}")
```

**Run it directly:**

```powershell
uv run python who_am_i.py
```

Output:

```
The __name__ is: __main__
```

**Now import it from another file:**

**File 2 — `importer.py`:**

```python
# importer.py
import who_am_i
print("---")
print(f"The __name__ is: {__name__}")
```

Run `importer.py`:

```powershell
uv run python importer.py
```

Output:

```
The __name__ is: who_am_i
---
The __name__ is: __main__
```

**The rule:**

- A module's `__name__` is `"__main__"` **only when it is the entry point** (the script you ran directly)
- Every module **imported** into it has `__name__` equal to its **module name** (the filename without `.py`)

**Visualizing the tree:**

```
You run: python importer.py
                          │
                          ▼
       importer.py  →  __name__ == "__main__"
                          │
                          │ imports
                          ▼
       who_am_i.py  →  __name__ == "who_am_i"
```

There is **exactly one** `"__main__"` per process: the entry script.

### 5. The `if __name__ == "__main__":` guard — why it exists

Here's the **problem** the guard solves:

Imagine `math_utils.py`:

```python
# math_utils.py
def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

# A quick test
print(add(2, 3))       # 5
print(multiply(2, 3))  # 6
```

Now `main.py` wants to use `math_utils`:

```python
# main.py
from math_utils import add

result = add(10, 20)
print(result)
```

Run it:

```powershell
uv run python main.py
```

Output:

```
5
6
30
```

**Where did `5` and `6` come from?** From `math_utils.py` — the `print()` calls ran **when the module was imported**. This is a **side effect on import**, and it's almost never what you want.

**The fix — the guard:**

```python
# math_utils.py (fixed)
def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

if __name__ == "__main__":
    # This runs ONLY when math_utils.py is executed directly
    # NOT when it's imported
    print(add(2, 3))       # 5
    print(multiply(2, 3))  # 6
```

Now:

- Running `uv run python math_utils.py` → runs the test prints ✅
- Running `uv run python main.py` → only prints `30` (no side effects) ✅

**This is the pattern.** Every professional Python script has it:

```python
def main():
    # actual program logic
    print("doing the work")

if __name__ == "__main__":
    main()
```

**Why `main()`?** Because you want the logic in a *function* (testable, reusable), and the guard just calls it. The function name `main` is a **convention** — Python doesn't care — but it's universal, so follow it.

---

### 6. The "Why" section — when does this actually matter?

**Scenario 1 — Library code.** A file that defines functions and classes may **also** have a demo at the bottom:

```python
# geometry.py
def area_circle(r):
    return 3.14159 * r * r

if __name__ == "__main__":
    print(f"Area of r=1: {area_circle(1)}")
```

Other code imports `area_circle` — no demo noise. Running the file directly shows the demo.

**Scenario 2 — CLI entry points.** Your script is *also* importable:

```python
# trainer.py
def train(model, data):
    ...

if __name__ == "__main__":
    from pathlib import Path
    data = load_data(Path("data.csv"))
    model = MyModel()
    train(model, data)
```

You can `from trainer import train` in a notebook, **and** run `python trainer.py` from the shell.

**Scenario 3 — Python packages.** When `pytest` imports `tests/test_math.py`, it does **not** want the test file to *execute* itself. The `if __name__ == "__main__":` guard prevents that:

```python
# tests/test_math.py
from math_utils import add

def test_add():
    assert add(2, 3) == 5

if __name__ == "__main__":
    # only run manually: `python tests/test_math.py`
    test_add()
```

`pytest` collects `test_add` and runs it. It does **not** run `test_add()` from the guard. If the file called `test_add()` unconditionally, `pytest` would double-run everything.

**Scenario 4 — multiprocessing on Windows.** A classic bug:

```python
# bad.py
import multiprocessing

def worker(x):
    return x * 2

# NO GUARD — breaks on Windows
pool = multiprocessing.Pool()
print(pool.map(worker, [1, 2, 3]))
```

On Windows, `multiprocessing` **re-imports the script** in every child process. Without the guard, the `Pool()` call runs again in each child → **infinite recursion** → "RuntimeError: An attempt has been made to start a new process before..." With the guard, it works:

```python
# good.py
import multiprocessing

def worker(x):
    return x * 2

if __name__ == "__main__":
    pool = multiprocessing.Pool()
    print(pool.map(worker, [1, 2, 3]))
```

**This is a real bug** every Windows Python developer hits **once** and never forgets. It's the reason the guard is so strongly recommended.

---

### 7. What about the REPL's `__name__`?

In the REPL, `__name__` is **also** `"__main__"`:

```python
>>> __name__
'__main__'
```

The REPL is treated as the entry point. That's why some scripts with `if __name__ == "__main__": main()` run in the REPL too.

**Note:** This is why you can `import who_am_i` inside the REPL and see `"who_am_i"` for the imported module — the same rule applies.

---

### 8. The `import` side-effect problem (a preview of Module 7)

There is a bigger principle at play here: **importing a module should not *do* things — it should just define them.**

- ✅ Importing `math_utils` defines `add`, `multiply`
- ❌ Importing `math_utils` should **not** print, open files, connect to databases, or start servers

The `if __name__ == "__main__":` guard is one tool for enforcing this. The other tool is **architecture** — putting side effects only in the entry point (`main.py`), and keeping libraries side-effect-free.

This will come up in **[[7.1 Import Mechanics]]** — the full story of `import`, `__init__.py`, and why import-time side effects are dangerous.

**For now:** just internalize the rule.

> **The `__main__` guard is not a Python requirement. It's a *discipline*.** Python will happily run a file with side effects on import. The guard is your way of saying: *"This code is for running, not importing."*

**Exercise 2 — The guard, with a proper `main()`.**

Refactor `personality.py`:

```python
# personality_v2.py
"""A clean script with a main() entry point."""

def greet(name: str) -> str:
    return f"Hello, {name}!"


def main() -> None:
    print(greet("Sara"))
    print(greet("Ali"))
    print(greet("Yusuf"))


if __name__ == "__main__":
    main()
```

Notice:
- No top-level `print()` statements
- All logic is inside functions
- The guard calls `main()`

This is the **standard shape** of a professional Python script. Compare to `personality.py` and feel the difference.

Create a file `_bad_module.py` (underscore prefix to keep it obvious):

```python
# _bad_module.py

print("Loading _bad_module...")
config = {"debug": True}
```


Run it again — no side effects on import. **This is the pattern.**

## ⚠️ Gotchas & Traps

1. **Forgetting the guard in a script that's ever imported.**  
   → If `math_utils.py` has `print(add(2, 3))` at the top level and someone `import`s it, that print fires. **Every time.** The guard prevents this.

2. **Thinking the guard *must* be at the bottom.**  
   → It's **convention** to be at the bottom (so functions are defined before `main()` runs), but Python doesn't require it. That said, always put it at the bottom. It's the idiom.

3. **Thinking `__name__` is always `"__main__"`.**  
   → It's `"__main__"` **only** for the entry script (or the REPL). For imported modules, it's the **module name**. This is the core concept.

4. **Naming your script `main.py` and importing it elsewhere.**  
   → `import main` will fail or behave weirdly. The module name `main` is fine but semantically confusing. Name entry scripts something else (`run.py`, `app.py`, `cli.py`).

5. **Importing a file whose module name shadows a standard library.**  
   → If you create `json.py` in the same directory as your script and `import json`, **your file wins**. It shadows the stdlib module. This is a classic silent bug. **Never name your files after stdlib modules.**

6. **Running `python script.py` from the REPL.**  
   → If you're inside the REPL (`>>>` prompt) and type `python script.py`, you get a `SyntaxError`. `python script.py` is a **shell command**, not Python syntax. Exit the REPL first (`exit()`).

7. **Assuming `if __name__ == "__main__":` is *required*.**  
   → It's **not required** — Python will run a script without it. It's **strongly recommended** to prevent side effects, especially on Windows with `multiprocessing`. Follow the convention.

8. **`from module import *` and the guard.**  
   → `from module import *` imports *everything* (functions, classes, constants) — but the `if __name__ == "__main__":` block does **not** run because the module is being imported, not run as main. That's the correct behavior. Don't try to "fix" this. `import *` is a separate anti-pattern (we'll cover in Module 7).

9. **The `multiprocessing` trap on Windows.**  
   → On **Linux/macOS**, `multiprocessing` uses `fork()`, which doesn't re-import the script. On **Windows**, it uses `spawn()`, which **does** re-import. So code that works on Linux will **break** on Windows without the guard. This is a **real production bug**.

10. **Using `__main__` in Jupyter.**  
    → In a Jupyter notebook, `__name__` is `"__main__"`. So `if __name__ == "__main__":` runs in a cell. This can be confusing if you're testing a library — use **`import`** in a notebook to avoid it.

11. **Thinking `main()` is special.**  
    → `main()` is **just a convention**. Python does not call it automatically. You must call it yourself in the guard:
    ```python
    if __name__ == "__main__":
        main()   # ← this line is what makes it run
    ```

12. **Placing `if __name__ == "__main__":` *above* function definitions.**  
    → Order of execution is top-to-bottom. If `main()` is defined *after* the guard, you get a `NameError`. **Functions first, guard last.** Always.
